**32-user profile.** All 32 requests arrive together, and each 4096-token prompt is prefilled in two 2048-token
chunks. The plugin interleaves one decode step per prefill chunk (`decode_interleave_prefill_steps 1`, the Stage 10
setting). Prefill therefore takes 31.4 s of the 44.0 s measured window, the median ITL is 27 ms, and TPOT and ITL p95
(216 ms) are dominated by decode steps waiting behind other users' prefill chunks. Measured from the roofline evidence: a
decode step between two decode steps with 30-32 active rows takes 25.8 ms (median of 201), and a 2048-token
prefill chunk takes 165.5 ms (median). The single-user decode (9.34 ms/token) matches Stage 10 (9.25 ms/token at 128 in / 128 out).

## Accuracy protocol
- **Harness and prompts.** Upstream lm-evaluation-harness 0.4.13 through the plugin's `benchmark_stage evaluate`,
  using the chat-completions endpoint. The server applies the model's native HF chat template exactly once
  (structured messages; the template opens `<think>`). Zero-shot, 32 concurrent requests, one shared request pool for
  both tasks (identical generation settings), upstream prompts and scorers.
- **Question subsets.** The packaged `ci-v1-reasoning.json` manifest (frozen before any score was observed):
  - GPQA Diamond: the first 128 of 198 in deterministic hash order, with the plugin's seed-0 choice shuffle.
  - IFEval: 256 of 541.
  - The manifest hash is in REPORT.md, and `run/manifest.json` is the frozen copy.
- **Generation settings.** temperature 0.6, `max_gen_toks` 32768, top_k 32, repetition_penalty 1.05, `until: []`
  (EOS only), and lm-eval's per-request seed 1234.
  - The published protocol is "vLLM, temperature 0.6, max output tokens 32768". vLLM would then also apply the
    checkpoint's `generation_config` (top_k 50, repetition_penalty 1.05).
  - **Protocol difference:** top_k 32 instead of 50. The device sampler keeps 32 candidates (Stage 10 decision for
    exact semantics). top_k 50 would run on the host sampler, at 155-165 ms per 32-row step. At temperature 0.6
    the probability mass beyond rank 32 is negligible.
  - Upstream `until` values were cleared because GPQA's `</s>` and stop strings in general can cut native reasoning.
- **Reasoning separation.** The server runs `--reasoning-parser deepseek_r1`, so text before `</think>` is returned as
  `reasoning` and only the final `content` is scored. A spot check of raw responses shows the answers are well
  formed.
- **Thinking and truncation.** Thinking is always on, as intended by the model.
  - GPQA: 118 responses ended with `stop` and 10 with `length` (7.8 %), all 10 with an empty final answer. They are
    kept in the denominator and score as wrong.
  - IFEval: 256 `stop`, 0 truncated.
  - The 10 truncated reasoning traces are coherent multi-step chemistry and genetics work still in progress at
    32768 tokens. A 60-character-chunk repetition count over the last 3000 characters is 1 for all of them, so
    there is no degenerate looping.
- **Strict-match 0.00 on GPQA.** Upstream strict-match needs the literal "The answer is (X)". No response uses that
  phrase (0 / 128); the model ends with forms such as "**Answer: (C)**" or "the correct choice is **(D)**".
  Flexible-extract takes the last "(X)" in the answer. Scores are upstream and not hand-corrected, and the reference
  is attached to flexible-extract.
- **Pilots** on documents outside the frozen subsets, used only to size the run (`session_state/stage11` /
  scratchpad):
  - IFEval, 32 prompts: mean 1738 tokens, max 4226, 0 truncated.
  - GPQA, 32 questions: mean 13.2k tokens, 6 / 32 reached 32768. Wall time 839 s.

## Roofline accounting
The collector is [tests/benchmark_roofline.py](../../tests/benchmark_roofline.py); its docstring gives the full method.
- **Timing.** Adapter call records, one per prefill / decode call, on CLOCK_MONOTONIC, which is the same clock as the
  client's `start_times`.
  - The window runs from the first measured request start to the last measured slot release: 12.07 s (b1) and
    44.00 s (b32), against client durations of 12.06 and 44.00 s.
  - Every interval from one call's start to the next call's start is charged to that call's phase, so the phases do
    not overlap, include host gaps, CCL, sampling and readback waits, and sum to the window.
  - The b1 phases are 2.36 s prefill and 9.69 s decode; b32 is 31.39 s and 12.57 s.
- **Request mapping.** Admissions inside the window must equal the measured requests: 8 and 96, 4096 prompt tokens
  each (32768 and 393216 tokens). Decode row-tokens reconcile exactly: 8 × 127 and 96 × 127, because each request's
  first token comes from prefill.
- **Work.**
  - Prefill: useful FLOPs (2 × active matmul parameters + causal attention + LM head once per request).
  - Decode: DRAM bytes at the C1 stored dtypes over 4 chips, covering weights, experts, KV reads/writes at the logged
    positions and ShortConv state. Experts: the compact bucket reads 4 × bucket; larger buckets read the union of the
    rows' top-4. The union is not logged, so it is modeled as the expected union under uniform routing, which is an
    upper-side estimate if routing is skewed.
  - The b1 step model is 704 MB per chip at position 192, consistent with Stage 7's 693 MB DRAM roofline.
- **Peaks.** tt-perf-report `blackhole` spec × 4 chips: 1.2165 PFLOP/s at HiFi2 (the policy's prefill fidelity) and
  2.048 TB/s DRAM.
- **Evidence.** `run/roofline-b{1,32}-evidence.json` (per-call segments), `run/roofline-b{1,32}-events.jsonl.xz` (raw
  window records) and `run/roofline.json`. Full logs are in `logs/*.xz`. The full 32-slot event log (100 MB, including
  the accuracy traffic) is outside git at `session_state/stage11/events-b32-20261019T035720.jsonl.xz`.
